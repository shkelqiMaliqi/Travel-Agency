Text To Explain

My project is a Travel Agency Portal built with React on the frontend and ASP.NET Core Web API on the backend. The system allows users to view destinations and travel packages, create bookings, manage their profile, reset passwords, and send contact messages. Admin users can manage places, hotels, packages, users, bookings, messages, and dashboard statistics.

For security, the project uses JWT authentication. After login, the client sends the JWT token in the Authorization header for protected requests. The project also uses role-based access control with three roles: user, admin, and auditor. Normal users can use customer features, admins can manage the system, and auditors have read-only access to audit and reporting data. MFA is implemented for privileged roles, meaning admin and auditor users must verify a one-time code before receiving the final JWT token.

The API is documented with Swagger and OpenAPI. Swagger UI allows developers to test endpoints directly from the browser, including authentication, request examples, response examples, and common error codes. The API is versioned using URL versioning, for example /api/v1/users and /api/v1/packages.

For performance and scalability, the project includes Redis-ready caching, NGINX gateway and load balancing configuration, RabbitMQ asynchronous processing, and background workers. RabbitMQ is used for queued MFA/email delivery, and the separate NotificationService consumes those messages in the background. This demonstrates microservice-style communication even though the main business API is still mostly a modular monolith.

For monitoring, logging, and auditing, the backend exposes a Prometheus-compatible /metrics endpoint. The infrastructure includes Prometheus, Grafana, Alertmanager, and ELK stack configuration. The application can ship logs to Logstash, and audit events are stored in SQL Server for security review. Admin and auditor users can view audit logs and metrics snapshots.

The project also integrates with external systems. It uses SQL Server as the relational database, EF Core as an ORM for support tables, MongoDB for optional analytics events, and S3-compatible storage through MinIO or cloud-style configuration. Docker and Docker Compose are included, and Kubernetes manifests are prepared for larger deployment environments.

For code quality, the project follows a clean modular structure with controllers, services, middleware, filters, models, and data layers. The frontend uses ESLint and Prettier, and the repository has an editor configuration. Automated tests exist for the backend, Playwright E2E tests exist for the frontend, and GitHub Actions are included for continuous testing.

The parts that are not fully production-ready are mainly deployment-related. Real SMTP credentials, Slack or email alert webhooks, TLS certificates, a real domain name, cloud storage credentials, and real staging or production hosting are not included because they require private accounts and real infrastructure. However, the project structure and configuration are ready for those features.

In conclusion, the project covers the main Web API requirements, including REST endpoints, JWT, RBAC, MFA, Swagger, versioning, caching, asynchronous processing, monitoring, logging, auditing, Docker, Kubernetes, and tests. Some enterprise features are demo-ready or infrastructure-ready, which is normal because full production deployment requires real external services and secrets.
